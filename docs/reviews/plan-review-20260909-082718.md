## Assumptions tested

1. A 中 `msw/node` 的 `setupServer` 能拦截 `useProductList` 经 axios 发出的 `/api/products` 请求。
2. B 的 `eslint.config.js` 用 `import.meta.dirname` 在目标环境可解析。
3. B 的 `recommendedTypeChecked` 不会让 A 的测试/setup 文件产生不可预期的新 lint 错误。
4. A 的测试断言写法在 strict/type-checked 下类型安全。

## Findings

### F1-未修复-[严重]-测试环境 axios 默认 XHR adapter 不会被 msw/node 拦截

- **位置**: Slice A §1.3 `src/test/setup.ts`、§1.4 `src/test/handlers.ts`、§1.6 `useProductList.test.tsx`；证据 `src/lib/request.ts:6`
- **问题类型**: 测试缺口 / 不可直接实施（happy-path 之外的基础失败）
- **当前写法**: plan 用 `setupServer(...handlers)`（来自 `msw/node`）拦截 `/api/products`，并假设断言能拿到 `data.list`；但未对请求层做任何 adapter 配置。
- **反例/失败场景**: `src/lib/request.ts` 用 `axios.create({ baseURL:'/' })`，**未指定 adapter**。axios 在 jsdom 环境下默认使用 **XHR adapter**；而 `msw/node` 的 `setupServer` 只拦截 Node 的 `fetch`/`http`，**不拦截 XHR**。结果：`useProductList` 发出的请求既不被 mock，也会因 jsdom 无对应服务端而失败 → 测试永远 `isSuccess=false`，`waitFor` 超时。
- **为什么有问题**: 这是 P0 唯一覆盖「数据请求」的测试，若失败则 Slice A 的 success signal（`npm run test` 通过）无法满足，plan 实际上**不可直接交给 implementation**。
- **直接证据**: `src/lib/request.ts:6` `const request = axios.create({...})`（无 adapter）；`package.json` axios `^1.17.0`（默认 XHR）；msw v2 `setupServer` 文档明确仅拦截 fetch/http。
- **影响**: implementation agent 按 plan 写完后测试必红；返工或被迫删测试。
- **建议改法和验证点**: 在 `src/test/setup.ts` 顶部显式将请求实例切到 fetch adapter（Node ≥18 提供全局 fetch，msw/node 可拦截 undici fetch）：
  ```ts
  import request from '@/lib/request'
  request.defaults.adapter = 'fetch'
  ```
  或等价地设置 `axios.defaults.adapter = 'fetch'`。验证：本地运行 `npm run test` 时 `useProductList` 通过且网络面板无真实请求发出。
- **修复风险**: 低（单点配置；不影响生产，因 setup 仅在测试加载）
- **严重程度**: 严重

### F2-未修复-[中]-`tsconfigRootDir: import.meta.dirname` 依赖 Node ≥ 20.11

- **位置**: Slice B §2.4 `eslint.config.js`
- **问题类型**: 环境假设 / 不可直接实施（部分环境）
- **当前写法**: `languageOptions.parserOptions = { project: './tsconfig.app.json', tsconfigRootDir: import.meta.dirname }`
- **反例/失败场景**: `import.meta.dirname` 在 Node < 20.11 不存在，CI/本地若是旧 Node 则 ESLint 直接抛错，`npm run lint` 失败。
- **为什么有问题**: 团队/CI 的 Node 版本未在本 plan 中声明，构成隐性环境耦合。
- **直接证据**: `import.meta.dirname` 为 Node 20.11+ 特性。
- **影响**: lint 在部分环境直接崩溃，B 的 success signal 无法满足。
- **建议改法和验证点**: 改为 `tsconfigRootDir: process.cwd()`（稳定、兼容更广），或在 README/eng 文档固定 Node 版本。验证：`node -v` 与 lint 在不同 Node 下均通过。
- **修复风险**: 低
- **严重程度**: 中

### F3-未修复-[中]-type-checked 上线后 A 的测试/setup 文件可能新增 lint 错误

- **位置**: Slice B §2.4 与 Slice A §1.3/§1.5/§1.6 的边界
- **问题类型**: 切片耦合 / 验证缺口
- **当前写法**: B 将 ESLint 升到 `recommendedTypeChecked`，但 plan 仅在 §1.8/§1.9 说「B 完成后需复跑 A」，未预见 type-checked 对测试文件的具体规则（如 `no-floating-promises`、`no-misused-promises`、`restrict-template-expressions`）。
- **反例/失败场景**: `setup.ts` 的 `beforeAll(() => server.listen({ onUnhandledRequest: 'error' }))` 在某些 type-checked 静态分析下可能触发 `no-floating-promises`/`no-misused-promises`；测试文件若使用被 type-checked 视为不安全的写法，`npm run lint` 在 B 后变红。
- **为什么有问题**: A、B 推荐顺序为 C→A→B；B 在 A 之后实施，会反向影响 A 已通过的 lint 状态，plan 未给出兜底（如针对 `src/test/**` 的 `overrides` 豁免或适配）。
- **直接证据**: `eslint.config.js` 当前全局 `files: ['**/*.{ts,tsx}']`，无测试目录豁免。
- **影响**: B 完成后 lint 红，需临时返工测试文件，破坏「每 slice 可独立 accept」的承诺。
- **建议改法和验证点**: 在 B 的 `eslint.config.js` 中为 `src/test/**` 增加 `overrides` 允许测试专用规则放宽（如关闭 `no-floating-promises`），并将「B 后复跑 `npm run lint` 与 `npm run test`」写入 B 的验证清单。验证：B 完成后两个命令均为绿。
- **修复风险**: 低
- **严重程度**: 中

### F4-未修复-[低]-`cartStore.test.ts` 使用非空断言 `items[0]!`

- **位置**: Slice A §1.5
- **问题类型**: 最佳实践偏离（测试稳健性）
- **当前写法**: `expect(items[0]!.quantity).toBe(1)`
- **反例/失败场景**: 一旦 `addItem` 行为变化导致 `items` 为空，断言给出 `undefined.quantity` 的混淆报错而非清晰失败。
- **影响**: 测试失败信息不直观，调试成本略增。
- **建议改法**: 改用 `expect(items[0]?.quantity).toBe(1)` 或在断言前先 `expect(items).toHaveLength(1)`。
- **修复风险**: 低
- **严重程度**: 低

### F5-未修复-[低/deferred]-测试仅覆盖 happy path

- **位置**: Slice A §1.6 / §1.9
- **问题类型**: 测试缺口（failure path 未证明）
- **当前写法**: `useProductList` 仅断言 `isSuccess` 与 `data.list.length>0`；购物车仅测增删改。
- **反例/失败场景**: 接口 500 / 网络异常时 hook 的 `isError`/`error` 分支未被验证，回归可能漏掉。
- **影响**: 属 P0 示例测试可接受范围，但后续 phase 应补失败路径（mock error 响应 + 断言 `isError`）。
- **建议改法**: 在 P1 或 P0 收尾时补一个「列表请求失败 → isError」用例（复用 `src/test/handlers.ts` 增加一个 error handler）。
- **修复风险**: 低
- **严重程度**: 低

### F6-未修复-[低]-`husky` 的 `prepare` 脚本在 CI/无 git 环境可能失败

- **位置**: Slice C §3.6
- **问题类型**: 环境耦合
- **当前写法**: `"prepare": "husky"`
- **反例/失败场景**: 某些 CI / 容器 / 无 `.git` 的场景下 `husky` 初始化失败，`npm ci` 中断。
- **影响**: 构建/部署失败。
- **建议改法**: 改为 `"prepare": "husky || true"`（按需），或仅在本地开发依赖中初始化。
- **修复风险**: 低
- **严重程度**: 低

## Conclusion

**`fail`** — Slice A 存在**严重 blocker（F1）**：测试环境未将 axios 切到 fetch adapter，`msw/node` 无法拦截 axios 的 XHR 请求，导致 `useProductList` 测试必然失败，plan 当前不可直接交给 implementation。F2 为中风险环境假设，应一并修复。F3–F6 为低/中风险，可在实施时顺带处理或 defer。

**处置**：在 plan 中补齐 F1（test setup 设 `request.defaults.adapter='fetch'`）、F2（`tsconfigRootDir: process.cwd()`）、F3（测试目录 ESLint `overrides`）后，本 plan 可进入 implementation。
