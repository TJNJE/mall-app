## Findings

### F1-未修复-中-RBAC 能力已实现但无任何路由使用 requiredRole（能力未生效）

- **入口/函数**: `AuthGuard` 的 `requiredRole` 参数
- **文件(行号)**: `src/lib/AuthGuard.tsx:20-22`；`src/lib/router.tsx`（所有 `<AuthGuard>` 均未传 `requiredRole`）
- **输入场景**: 任何受保护路由的访问
- **实际分支**: `AuthGuard` 仅执行「是否登录」判断，`requiredRole` 分支永远不会被命中
- **预期行为**: 依 plan S5 success signal「RBAC：`AuthGuard` 支持 `requiredRole`，无权限跳转 403/登录」
- **实际行为**: RBAC 代码路径存在但不可达——`/403` 分支实际不会被触发，等价于只交付了登录态守卫
- **直接证据**: `router.tsx` 中 4 处 `<AuthGuard>` 包裹均未传 `requiredRole`；仓库中无 `requiredRole=` 的使用点
- **影响**: 权限能力形同虚设；后续若有人认为「已实现 RBAC」而实际无路由受角色保护，会产生错误的安全预期
- **建议改法和验证点**: 为需要角色保护的路由显式配置 `requiredRole`（演示级可对某路由配 `'admin'`），或提供 admin 登录入口以便验证；验证点：以 `role='user'` 访问该路由应重定向到 `/403`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
- **裁决**: deferred-with-owner（当前无真实角色体系与 admin 账号来源，见 F2；接入后端权限后统一配置）

### F2-未修复-低-不存在 admin 登录路径，/403 分支不可达

- **入口/函数**: `login(username, role = 'user')`
- **文件(行号)**: `src/features/auth/stores/authStore.ts:18`
- **输入场景**: 用户登录
- **实际分支**: `LoginPage` 调用 `login(username)`，role 恒为默认值 `'user'`
- **预期行为**: 若 RBAC 要可验证，需存在产生非 `user` 角色的途径
- **实际行为**: 所有登录用户都是 `user`，`user?.role !== requiredRole` 在该设定下永不成立
- **直接证据**: `LoginPage` 未传第二个参数；mock/后端登录响应未接入角色（登录走 store，不经 api）
- **影响**: 与 F1 叠加，导致 RBAC 无法端到端演示/验证
- **建议改法和验证点**: 接入真实登录接口返回角色，或在演示环境提供角色选择；验证点：能以 admin 身份登录并访问受保护路由
- **修复风险（低/中/高）**: 中（涉及登录链路改造）
- **严重程度（低/中/高/严重）**: 低
- **裁决**: deferred-with-owner（同 F1，待后端权限契约）

### F3-已修复-低-hydrate 对损坏的 localStorage 数据无异常处理，可导致启动即白屏

- **入口/函数**: `hydrate()`
- **文件(行号)**: `src/features/auth/stores/authStore.ts:31-44`（fix 后）
- **输入场景**: `localStorage['__mall_user__']` 存有非 JSON 内容（如手工写入或旧版本残留）
- **实际分支**: 原 `JSON.parse(saved) as User` 直接执行，无 `try/catch`
- **预期行为**: 启动阶段的数据异常不应让整个应用无法渲染
- **实际行为**: `JSON.parse` 抛 `SyntaxError`，且 `hydrateAuth()` 在 `RouterProvider` 中同步调用，异常会向上冒泡导致应用渲染失败（白屏）
- **直接证据**: 原实现 `const user = JSON.parse(saved) as User` 无异常处理；`router.tsx:29` 顶层调用 `hydrateAuth()`
- **影响**: 健壮性缺陷——单个损坏的本地存储项即可让已登录用户完全无法使用应用（这是 S4 白屏检测想发现、但本可避免的场景）
- **建议改法和验证点**: `try/catch` 包裹解析，失败时清理该存储项并登出
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
- **fix 验证**: 已改为 `try/catch` + `logger.warn` + 清理存储项；`npm run build` / `lint` / `test` 均通过
