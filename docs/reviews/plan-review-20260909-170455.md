# Plan Review — Phase 3 (P2) 治理能力补齐

- **reviewed target**: `docs/gateflow/eng-gaps-phase3-plan.md`
- **scope**: 6 slices（S1 架构边界 / S2 提交规范 / S3 API 契约 / S4 安全 / S5 设计系统 / S6 文档治理）
- **assumptions tested**: 存量违规仅 request.ts 一处；暗黑「全站生效」成立；CSP meta 不阻断 dev；schema.d.ts 与 src/types 可并存；cruiser 支持 `$1` 反向引用；husky 9 hook 格式

## Findings

### F1-未修复-中-存量 lib→features 违规不止一处，注入改造清单不完整

- **位置**: S1 implementation decisions「预期存量违规」
- **问题类型**: 不可直接实施
- **当前写法**: 仅识别 `request.ts` 一处违规，处置为 token getter 注入
- **反例/失败场景**: 改完 request.ts 后 cruise 仍红——`src/lib/hydrateAuth.ts:1` 同样违规（`import { useAuthStore } from '@/features/auth/stores/authStore'`），实施 agent 被迫现场决策
- **为什么有问题**: S1 success signal「cruise 全绿（违规已修复/豁免）」以完整违规清单为前提，清单不完整则信号不可达
- **直接证据**: `hydrateAuth.ts:1`；该文件在 router 启动链路（`router.tsx:5`）
- **影响**: 实施 Agent 跑偏 / slice 无法收口
- **建议改法和验证点**: 补全处置——将 hydrateAuth 迁移至 `src/features/auth/lib/`（auth 状态的 hydrate 逻辑归属 auth feature），router.tsx 改 import；验证点：cruise 对 lib→features 规则全绿
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F2-未修复-中-暗黑模式「全站 token 生效」在硬编码色组件上不成立，范围被低估

- **位置**: S5 success signal / implementation decisions
- **问题类型**: 范围漂移
- **当前写法**: 「切换后全站 token 生效并持久化」
- **反例/失败场景**: toggle 加 `.dark` 类后页面视觉无变化——现有组件全部硬编码 Tailwind 灰阶（`bg-white`、`text-gray-800`），不读取 token；实施 agent 要么交付假效果，要么现场扩 scope 全站补 `dark:` 变体
- **为什么有问题**: `globals.css` 仅 9 个品牌色 token，无语义灰阶变量；「全站生效」与「首批组件」工作量差一个数量级
- **直接证据**: `globals.css` @theme 仅 `--color-primary/-hover/danger/success/warning/text/text-secondary/muted/price`
- **影响**: 假交付或 scope 膨胀
- **建议改法和验证点**: 收窄为三层——(a) @theme 补语义灰阶并在 `.dark` 下覆盖；(b) toggle + 持久化 + 跟随系统；(c) 首批 3-5 个核心组件/页面适配；全站适配显式 defer
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F3-未修复-中-CSP 放 meta 的决策大概率直接阻断 Vite dev，「先 meta 后降级」是可预期返工

- **位置**: S4 implementation decisions
- **问题类型**: 非最优方案
- **当前写法**: index.html 加 CSP meta，若阻断 dev 再降级
- **反例/失败场景**: Vite dev 注入 inline script（@vite/client preamble）+ HMR ws，meta `script-src 'self'` 直接拦截 → dev 立即白屏，实施 agent 必然先破坏再回退
- **为什么有问题**: 已知大概率失败的路径不应作为首选；prod-only 注入无回退成本
- **直接证据**: Vite dev 机制；plan 自身已预写降级路径（自我印证）
- **影响**: 实施返工 / dev 中断 / 半成品配置
- **建议改法和验证点**: 决策前置为 prod-only——自写 `transformIndexHtml` 钩子（`apply: 'build'`，约 10 行）在构建时注入 CSP meta；验证点：build 产物 html 含 CSP、dev 正常
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F4-未修复-中-schema.d.ts 与 src/types 形成双真源，处置策略缺失

- **位置**: S3 affected files / implementation decisions
- **问题类型**: 契约缺失
- **当前写法**: api 层改引生成类型；未提 src/types/index.ts 去留
- **反例/失败场景**: `src/types` 被 8 个文件消费（handlers、3 hooks、2 pages、request、api）；只改 api 层 → `Product` 两份独立定义，字段漂移无告警；现场删 types 则 8 文件连锁改动超出 slice 预期
- **为什么有问题**: 「契约成为真源」是本 slice 目标，保留手写副本直接违背
- **直接证据**: `grep -rln "from '@/types'" src | wc -l` = 8
- **影响**: 类型漂移 / scope 膨胀
- **建议改法和验证点**: 明确策略——src/types/index.ts 改为从 schema **re-export**（`export type Product = components['schemas']['Product']`），8 个消费方零改动，单一真源落 yaml；schema 命名与现有类型对齐（Product/ProductListResponse/Order/OrderListResponse/CheckoutRequest/CheckoutResponse/ApiResponse/ApiError），核对表入 impl artifact
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### F5-未修复-低-cruiser 捕获组反向引用（`$1`）语法未验证

- **位置**: S1 规则 4（no-cross-feature）
- **问题类型**: 技术假设未证
- **当前写法**: `from: 'src/features/([^/]+)/'` + `to: 'src/features/(?!$1/)[^/]+'`
- **反例/失败场景**: 若不支持 to 中引用 from 捕获组，规则无法成立
- **为什么有问题**: 跨 feature 规则是 S1 核心规则之一
- **直接证据**: 语法依赖 cruiser 文档行为，plan 未安排验证
- **影响**: 规则退化（枚举 features 列表）
- **建议改法和验证点**: S1 实现第一步用单规则反例验证该语法并记录；不支持则降级为显式枚举
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### F6-未修复-低-husky 9 的 commit-msg hook 文件格式未写明

- **位置**: S2 implementation decisions
- **问题类型**: 不可直接实施（轻微）
- **当前写法**: 仅写 hook 内容命令，未注明 husky 9 格式（无 shebang，直接命令，与现有 `.husky/pre-commit` 一致）
- **反例/失败场景**: 实施 agent 按 husky 8 习惯加 shebang 或 chmod，可能困惑
- **直接证据**: 项目 husky `^9.1.7`，现有 `.husky/pre-commit` 是格式模板
- **影响**: 轻微
- **建议改法和验证点**: plan 注明「格式照抄现有 pre-commit，无 shebang」
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
