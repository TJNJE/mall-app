### F1-已修复-低-未限制 GITHUB_TOKEN 权限（最小权限原则）

- **入口/函数**: workflow 顶层配置
- **文件(行号)**: `.github/workflows/ci.yml:8-10`（fix 后位置）
- **输入场景**: workflow 在 GitHub Actions 中运行，自动获得 `GITHUB_TOKEN`
- **实际分支**: 原未声明 `permissions`，token 沿用仓库默认权限（可能为可写）
- **预期行为**: CI 只需读取代码，应遵循最小权限原则显式收敛为只读
- **实际行为**: 未显式限制，token 权限取决于仓库设置，存在被过度授予写权限的可能
- **直接证据**: 原 workflow 文件中仅有 `on` / `jobs.ci.runs-on` / `steps`，无 `permissions:` 声明
- **影响**: 安全面——若某个步骤（或将来加入的第三方 action）被攻陷，可凭过宽 token 权限写入仓库
- **建议改法和验证点**: 在 workflow 顶层加 `permissions: contents: read`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
- **fix 验证**: 已加入 `permissions: contents: read`；`ruby -ryaml` 解析输出 `permissions={"contents"=>"read"}` 且 `YAML_OK`

### F2-已修复-低-缺少 concurrency 控制，并发推送会重复占用 runner

- **入口/函数**: workflow 顶层配置
- **文件(行号)**: `.github/workflows/ci.yml:12-15`（fix 后位置）
- **输入场景**: 同一分支连续推送多次，或多个 PR 同时更新
- **实际分支**: 每次推送都会启动新的 workflow run，旧的仍在跑
- **预期行为**: 同一分支/PR 的过期运行应被自动取消，节省 runner 时间
- **实际行为**: 未声明 `concurrency`，不取消任何运行
- **直接证据**: 原 workflow 文件中无 `concurrency:` 声明
- **影响**: 成本面——快速连续推送会产生多个并行运行，浪费 CI 时长
- **建议改法和验证点**: 加 `concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
- **fix 验证**: 已加入 `concurrency`；解析输出 `concurrency={"group"=>"ci-${{ github.ref }}", "cancel-in-progress"=>true}` 且 `YAML_OK`
