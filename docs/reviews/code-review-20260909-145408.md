## Findings

### F1-未修复-中-plan 要求的 brotli 压缩未产出任何 `.br` 文件

- **入口/函数**: Vite 构建插件 `viteCompression({ algorithm: 'brotliCompress', ext: '.br' })`
- **文件(行号)**: `vite.config.ts`（原 brotli 实例位置，现已移除并留注释）
- **输入场景**: 执行 `npm run build`
- **实际分支**: 仅 gzip 实例生效；brotli 实例未产出任何文件
- **预期行为**: 依 `docs/gateflow/eng-gaps-phase2-plan.md` S2 success signal，「`dist` 含 `.gz` / `.br` 压缩文件」
- **实际行为**: brotli 插件自身打印 `compressed file successfully`，但 `find dist -name "*.br"` 返回空；`dist` 根目录仅有 `assets/ favicon.svg icons.svg index.html mockServiceWorker.js stats.html`，不存在路径拼接产生的 `dist/Users/...` 嵌套目录，排除「输出到异常路径」的可能
- **直接证据**: build 日志中 gzip 段落列出了具体文件，brotli 段落仅有标题、无文件列表；`ls dist/assets/*.br` 报 `no matches found`；移除 brotli 实例后 build 仍成功（说明它此前确实无贡献）
- **影响**: 压缩能力不完整（仅 gzip）；保留无效配置会让读者误以为 brotli 已生效
- **建议改法和验证点**: 换用专门支持 brotli 的插件（如 `vite-plugin-brotli` / `rollup-plugin-brotli`），或确认 `vite-plugin-compression` 多实例在 Vite 8 / rolldown 下的兼容修复；验证点：`npm run build` 后 `ls dist/assets/*.br` 有产物
- **修复风险（低/中/高）**: 中（需替换插件并重新验证产物）
- **严重程度（低/中/高/严重）**: 中
- **裁决**: deferred-with-owner（gzip 已覆盖主要压缩场景）

### F2-已修复-中-visualizer 常驻使生产构建显著变慢

- **入口/函数**: `visualizer()` 插件（原本无条件加入 plugins）

- **输入场景**: 每次 `npm run build`（含 CI 中的 build 步骤）

- **预期行为**: 包体积分析属按需诊断手段，不应拖慢常规构建

- **建议改法和验证点**: 用环境变量控制，仅在需要时启用
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
- **fix 验证**: 已改为 `ANALYZE=1` 按需启用；默认 `npm run build` 后 `ls dist/stats.html` 返回 `NO_STATS_OK`，gzip 产物 12 个正常产出

### F3-已修复-低-体积预算 500 kB 相对实际体积过松，无约束效果

- **入口/函数**: `size-limit` 配置
- **文件(行号)**: `package.json:18-23`
- **输入场景**: 执行 `npm run size`（CI 中用于拦截体积膨胀）
- **实际分支**: 原预算 `limit: "500 kB"`，实测 `Size: 130.88 kB brotlied`
- **预期行为**: 预算应在接近实际上限时触发告警，起到拦截作用
- **实际行为**: 实际体积仅为原预算的 26%，体积需增长近 4 倍才会失败，短期内无任何约束效果
- **直接证据**: `npm run size` 输出 `Size limit: 500 kB / Size: 130.88 kB brotlied`
- **影响**: 体积预算形同虚设，无法在体积回归早期告警
- **建议改法和验证点**: 将预算收紧到实际值附近，留出余量
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
- **fix 验证**: 预算收紧为 `200 kB`；`npm run size` 输出 `Size limit: 200 kB / Size: 130.88 kB brotlied`，仍通过
