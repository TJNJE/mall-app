# Plan Review — Phase 2 (P1) 工程化补齐

- **reviewed target**: `docs/gateflow/eng-gaps-phase2-plan.md`
- **scope**: 5 slices（S1 性能 / S2 构建 / S3 CI / S4 可观测 / S5 权限）
- **assumptions tested**:
  - React Compiler 与 `@vitejs/plugin-react` v6 的启用 API
  - `authStore.login` 返回 `role`
  - `manualChunks` 对象映射足够
  - Sentry 无 DSN 时安全降级
  - slice 执行顺序无关
  - 路由 PV 在 `App` 内 `useLocation` 可用

## Findings

### F1-未修复-中-S1/S4 对 ProductCard 的修改存在顺序耦合

- **位置**: S1 implementation（ProductCard memo+onOpen）与 S4（ProductCard 曝光 `track`）
- **问题类型**: 切片过粗 / 顺序耦合 / overcoupling
- **当前写法**: S1 重构 `ProductCard` 为 `memo`+`onOpen`；S4 在 `ProductCard` 内加 `IntersectionObserver` 曝光 `track`。两 slice 都改同一组件，但 plan 未定义执行顺序。
- **反例**: 若 S4 先于 S1 实现，`ProductCard` 仍是未 memo 版本；若 S1 先但 S4 的 `track()`（`src/lib/track.ts`）尚未创建，S1 引用 `track` 会编译失败（未定义导入）。
- **为什么有问题**: `track()` 属 S4 才创建的 lib，S1 过早引用产生跨 slice 编译依赖；memo 与 observer 同在卡片也易冲突。
- **直接证据**: plan S1 用 `queryClient.prefetchQuery`（S1 内自洽），但 S4 "ProductCard 曝光 track" 引用 S4 才创建的 `track()`。
- **影响**: implementation agent 按任意顺序会得到编译错误或漏 memo 的卡片。
- **建议改法**: plan 增加 "slice 执行顺序" 小节，明确 S4 的 `track` lib 先于 S1 曝光部分，或 S1 不含曝光、曝光统一在 S4 加（顺序 S1→…→S4）。
- **修复风险**: 低 / **严重程度**: 中

### F2-未修复-中-S5 的 User.role 来源契约未收敛

- **位置**: S5 contract / implementation（`authStore.login` 返回 role）
- **问题类型**: 契约缺失 / 假设未证
- **当前写法**: plan 称 "authStore.login 返回的 user 含 role（mock handlers 登录响应加 role）"，并给 `AuthGuard` `requiredRole` 判定 `user?.role`。
- **反例**: 实际 `authStore.login` 签名为 `(username: string) => void`，内部 `const user: User = { id, username, token }` 无 role（`src/features/auth/stores/authStore.ts:18-23`）；`User` 类型无 role（`src/features/auth/types/index.ts:1-5`）；`LoginPage` 直接调 `store.login(username)`，不经 api/mock 获取 role，故 "mock 登录响应加 role" 无法流入 store。
- **为什么有问题**: plan 假设 role 自动存在于 user，但现有登录链路不产生 role，S5 实现会卡在 "role 从哪来"。
- **直接证据**: `authStore.ts:18-23`；`types/index.ts:1-5`；mock 登录响应未证实含 role。
- **影响**: S5 RBAC 无法演示（`user.role` 恒 undefined → 所有 `requiredRole` 重定向）。
- **建议改法**: plan 明确 role 来源——(a) `authStore.login` 改为 `login(username, role: 'admin'|'user' = 'user')` 默认 `'user'`（演示级最小改动）；或 (b) `LoginPage` 经 `api.login` 获取带 role 的 user 再 `store.login(user)`（接后端用）。推荐 (a)。
- **修复风险**: 低 / **严重程度**: 中

### F3-未修复-低-S2 manualChunks 用对象映射可能遗漏传递依赖

- **位置**: S2 implementation decisions（`manualChunks` 对象）
- **问题类型**: 最佳实践偏离 / 非最优方案
- **当前写法**: `manualChunks: { react:['react','react-dom'], 'react-query':['@tanstack/react-query'], ... }`
- **反例**: `react-router-dom` 内部依赖 react/react-dom，对象映射不会归并其 react 引用，可能警告或重复；新增依赖不自动归类。
- **建议改法**: 用函数式 `manualChunks: ({ id }) => { if (id.includes('node_modules')) { if (id.includes('react')) return 'react-vendor'; ... } }` 更稳。
- **修复风险**: 低 / **严重程度**: 低

### F4-未修复-低-S4 性能/埋点初始化时机未明确

- **位置**: S4 affected files（`main.tsx` `initMonitor`）+ `perf.ts`
- **问题类型**: 测试缺口 / 最佳实践偏离
- **当前写法**: `initMonitor` 在 `main.tsx` 顶部调用；`PerformanceObserver` 采集 FCP/LCP/CLS 但何时注册未明确。
- **反例**: LCP/CLS 需在首屏渲染前注册 observer，若 `perf` 注册晚于首屏会错过指标。
- **建议改法**: 在 `initMonitor()` 内同步注册 `PerformanceObserver`（或 `main.tsx` render 前调用 `reportWebVitals()`），确保尽早。
- **修复风险**: 低 / **严重程度**: 低

### F5-未修复-低-缺 slice 执行顺序定义

- **位置**: 全局（5 slices 之间）
- **问题类型**: 切片过粗 / sequencing
- **当前写法**: 5 slice 并列，未给执行顺序与依赖。
- **建议改法**: 增加 "执行顺序"：S1→S2→S3→S5→S4，并明确 S4 的 `track` lib 先于 S1 曝光（或曝光在 S4 统一加）。
- **修复风险**: 低 / **严重程度**: 低

| 风险            | 分类                   | 去向                              |

| F3 manualChunks | fixed-in-current-slice | S2 用函数式                       |

## Conclusion

**pass-with-risks**。Plan 整体 code-generation-ready，5 slice 的目标/非目标/证据/验证清晰，无结构性 blocker。5 个 findings 均为低/中且可在 implementation 内以低成本消解（F2 需 S5 明确 `login` 改造为最小 `'user'` 默认；F1/F5 需约定 slice 顺序）。建议在进入 implementation 前于 plan 补充两条：(1) slice 执行顺序；(2) S5 role 来源（推荐 `login` 默认 `'user'`）。这些不影响 plan 交付，implementation gate 会覆盖。
